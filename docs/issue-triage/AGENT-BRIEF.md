## 3.5 ⚠️ 引用行号的三条纪律（本项目实测踩出来的）

吐槽板 `docs\mcp-吐槽板.md` **正在被主代理和另一个并行会话持续改写**，而内置工具的行号输出**本身也不可靠**：

| 坑 | 实测现象 | 正确做法 |
|---|---|---|
| **板子在动** | 行号在一次会话内 504 → 510 → 537 → 551 → 609；某条目从 79 行漂到 129 行 | **不要用行号定位条目**，用标题文本做锚点 |
| **`read` 工具行号漂移** | 有子代理实测：对吐槽板**少报 27 行**、对 `AGENT-BRIEF.md` 少报 1 行，**且同一文件内偏移还不一致** | `read` **看内容**可以；**要写进行号的**必须另用一种方式复核 |
| **续读 tip 不可信** | 外部 `read_file` 的 tip 行号比真实下一行少 1，照 tip 续读会重复最后一行 | 别把 tip 当真值 |

**定位条目的正确姿势**（不依赖任何工具的行号输出）：

```powershell
# 用标题文本做锚点
Select-String -Path '...\mcp-吐槽板.md' -Pattern '^## \[05\]'

# 或直接切出整段
[System.IO.File]::ReadAllText('...\mcp-吐槽板.md') | Select-String -Pattern '(?s)## \[05\].*?(?=## \[|\z)'
```

**要写进报告/计划的行号**，用 `[System.IO.File]::ReadAllLines(...)` 复核后再写。
**凡是没复核过的行号，宁可不写** —— 本流水线的全部价值建立在 `file:line` 引用逐字可核上，掺进一条幻觉会连累后面所有判断。

### 🚨「精确匹配 = 1」≠「锚点唯一」——**改完要核落点，不只核匹配数**（2026-10-04 对端实例，我这一晚反复栽）

对端侧：控制者按**整行精确匹配**断言某调用点"唯一"（数到 1）⇒ 登记代理实测**是 2 次**
（`:36` 在 `RunAll` 内、`:965` 在 DebugAction 处理器内）——
**另一处只是带了尾注释，所以那条正则没匹配上**。

⇒ 📌 **"pattern 只匹配到 1 处"只证明"只有 1 处长得这样"，不证明"只有 1 处该改"。**
**匹配数唯一 ≠ 落点唯一。**

**处置示范（比我预想的好）**：尊重派工词给的落点 `:36`，但把 `old_string` 从**单行**换成**两行块**
⇒ **落点物理唯一**，**不可能落进 `:965`**。
⇒ **规律**：**锚点越短越容易被"带尾注释的孪生兄弟"躲开；加长到多行块，物理唯一。**

⇒ **配套硬规矩**：
1. **锚点用 ≥2 行的连续块**，不要用裸的单行/短行。
2. 🚫 **不用别人的标题行、纯状态行、或任何"通用短行"当锚点** —— 只用**自己刚写的那一段**。
   （本项目已因此连撞多次 `file changed since it was read` / `old_string not found`。）
3. **改完必须核落点**：确认改到的是**预期那一处**，而不只是"工具返回了成功"。
4. **锚点类判断必须由【落盘者】复核，不能由【派工者】断言** —— 我给子代理的派单里的行号一律标注「须自行复核」。

### ⚠️ 工具用法陷阱（本项目实测踩过）

**`search_string_literals` 的 `pattern` 默认按「字面量」匹配，不是正则。**
曾有子代理用 `inputSchema|schema|parameters` 这种带 `|` 的模式检索 → 回 0 命中 →
**被当成「这些字符串不存在」的证据写进了报告。实际是模式写法无效。**

⇒ **带 `|` 的检索结论一律无效**，要么拆成多次字面量检索，要么先确认该工具的正则开关。
⇒ 这正是 COMMON.md §5.1 说的「零命中最危险的假阴性」——**在工具层面同样成立**。

### 🚨🚨 decompilerserver 的 current context 是**跨会话共享的全局可变状态**

**这是本项目最隐蔽的一个坑（2026-10-03 由维护者确认）。**

`mcp__decompilerserver__*` 的「当前上下文」**不是每个会话私有的** ——
**另一个并行会话调用同一个 MCP 服务器，就会把它挪走。**
已真实发生：**另一个并行会话拿同一工具去反编译 Pathos（不是 RimWorld）**，
把本会话的 current context 漂到了 `gab`（`Lib.GAB.dll`，仅 94 个类型）。

⇒ 此时 `search_symbols{query:"GetPathContext"}` 返回 `{"items":[],"totalEstimate":0}`，
**与「这个符号不存在」逐字同形** ⇒ 直接产出假结论。

**硬规则**：
1. **每一次 `mcp__decompilerserver__*` 调用都必须显式带 `contextAlias:"vanilla"`**
   （本环境 `vanilla` / `game` / `default` / `rw16` 四个别名指向同一 MVID `61e4173561894da49d210260257b5097`）。
2. **绝不用「不带 alias 的零命中」当证据** —— 不带 alias 的结果**连"没搜到"都不算**。
3. 若某次查询**来不及加 alias** ⇒ 在报告里标注「**该结论未经 alias 确认，待重验**」，**不要当既成事实往下传**。
4. 💡 通用形态：**「0 结果」必须附带「在哪儿搜的」才算证据** ——
   `COMMON.md §5.1` 要求零命中附检索式，**这里要附的是检索范围**。

### 🚨🚨 但**优先不要用 decompilerserver** —— 它是跨会话共享状态，本流水线会去挪它

**维护者 2026-10-03 定规（TEXT20 侧同规，两侧一致）：**

> **两侧都改为「每次调用显式传 `contextAlias`」，不再依赖 `current`。**
> **不要 `load_assembly(..., makeCurrent: true)`，也不要 `select_context` 去抢 `current`** ——
> 抢了当前**只是让自己下次调用「忘记传 alias」时踩坑**，对谁都没好处。**代价是零，收益是两边都不可能被串味。**

#### 别名按「你实际在查哪个程序集」选 ⚠️ **不要一刀切**

| 你要查的东西 | 该传的 `contextAlias` |
|---|---|
| **vanilla**（`Verse.*` / `RimWorld.*` / Assembly-CSharp，16158 类型） | **`vanilla`**（`game` / `default` / `rw16` 是**同一个 MVID `61e4173561894da49d210260257b5097`** 的等价别名，任选） |
| **`Lib.GAB.dll`**（GABP 库、94 类型） | **`gab`** |
| RBS 主程序集 / Core / Gabp.Runtime | 见 `list_contexts` 的实际 alias（此前用过 `rbs` / `rbscore`） |
| Harmony（版本敏感，**逐个版本 alias 不同**） | 先 `list_contexts` 确认，再显式传 |

⚠️ **我们这边绝大多数问题是查 vanilla**（`Verse.Map`、`RegionType`、Cecil、Harmony 语义）⇒ **默认用 `vanilla`**；
`gab` 只在查 `Lib.GAB.dll` 时用。

#### ⚠️ 唯一要提防的：读到「奇怪的代码」先查 MVID，**别先怀疑代码**

若某次反编译出来的代码**看着不对劲**（方法体空的、成员缺失、语义明显不是 vanilla）：
1. **先 `mcp__decompilerserver__list_contexts` 看 MVID**，确认当前 alias 指向哪个程序集；
2. 若 `game` 读不出来，**换 `rw16` / `vanilla` / `default`** —— **四个都指向同一 MVID**；
3. **确认无误后仍不对，才去怀疑代码/程序集本身。**

> **本流水线的定位**：我们这边很多问题**只能靠反编译**（C# 源码侧看不到的部分），
> 所以**该用就用**，但**必须带 alias、且绝不抢 current**。

**工具优先级（不变）**：
1. **首选 `mcp__rimworld-source-online__*`**（`search_source` / `read_file` / `read_csharp_symbol` / `search_defs` / `list_directory`）—— 不碰共享状态
2. **文件系统 grep / `[System.IO.File]::ReadAllLines`** —— 永远安全，核行号优先
3. **decompilerserver** —— 只在「必须查 IL / 元数据 / 源码索引里根本没有该成员」时用，**且必带 `contextAlias`**

> 这条与 [37] 是同一件事的两面：**工具的共享可变状态是跨会话的污染源**。

> 这与下面的「行号纪律」是同一类问题的两个面：
> **工具的输出必须带着「它凭什么这么说」的元信息**，否则沉默的失败会被读成肯定的成功（或失败）。

### 🚨🚨 禁止用 `pwsh` 改文件 —— 只用 `edit` / `write`

**本项目已发生真实事故（2026-10-02 23:17）**：一名子代理想用一条 PowerShell 命令把计划里的一整块（「规矩 4」）从「规矩 3」前面移到后面，**结果把整个 1212 行的计划覆写成 0 字节**。

**事故链（四步，每一步单独看都像没事）**：
1. `$new = @()` 建出的是 `Object[]`，**不是** `List[string]`；
2. 后面三次 `.AddRange(...)` **全部抛异常**；
3. ⚠️ **但脚本没有终止**（没有 `$ErrorActionPreference = 'Stop'`）⇒ 控制流继续往下走；
4. `WriteAllLines($p, $new)` 用那个**空数组**覆写了文件。

**而且没有备份可恢复** —— 本仓库**不是 git 仓库**，文件不在任何版本控制下。

**硬规则**：
1. **行级重排 / 插入 / 删除 ⇒ 只能用 `edit` 工具，绝不能用 shell 脚本。**
   两者的失败模式截然不同：`edit` 是「**不匹配 ⇒ 报错、文件不动**」；`WriteAllLines` 是「**静默写成空**」。
2. **任何写文件的 PowerShell 脚本，第一行必须是 `$ErrorActionPreference = 'Stop'`。**
   没有它，异常**不会终止脚本**，后续语句照跑不误。
3. **写完立刻核对行数**（`[System.IO.File]::ReadAllLines($p).Count`），不要闷头往下走。
4. 动别人的文件之前，**先确认目标路径不是自己那一个**。

> 💡 讽刺的是 COMMON.md §9 早就写着「**绝不要一次性输出大文件**」，还附了一次实测事故（卡 65 分钟、盘上一个字没有）。
> **但它没覆盖这一类：用 shell 做文本处理。** 现在补上了。

## 3.7 💡 十二条「通用形态」——TEXT20 侧数月反复咬人的（2026-10-03 交换）

**它们的共同根**：
> **全都是「用一个便宜的成功判据（计数 / 绿灯 / 状态位 / 名字）替代昂贵的事实核对」。省钱的那一刻，正好是证据失效的那一刻。**

| # | 形态 | 对策 |
|:--:|---|---|
| 1 | **「文档里写着」≠「我数过」** —— 转抄别人的表会**连错误一起抄**，且错误因转抄而**更可信** | 凡引用二手表格，**标注来源并重测**；不采信也不转抄 |
| 2 | **阈值基线取错 ⇒ 反向假绿**（基线 16 / 实为 17 / 门槛 26；少登记 1 条得 26 ⇒ **照样通过**） | **门槛与基线分别独立实测**；门槛写成**相对增量**而非绝对数 |
| 3 | **绝对数字门禁在「多份叠加」场景必为红** | 改**下限**或**增量**；绝对数只在单档独占时成立 |
| 4 | **「0 结果」必须附「在哪儿搜的」**（不只附检索式，还要附检索范围） | 见 §3.5 decompilerserver 段 |
| 5 | **恒真断言伪装成判据** —— 在/不在**殊途同归**返同一值，判别力=0 但它**绿着** | 自问：**「这条断言能不能失败？」** 不能 ⇒ 它是装饰，不是判据 |
| 6 | **读日志的「最后一行」≠ 结论** —— 倒序日志末行是帧噪声；某些控制台**每行回显两遍** | 认**行首锚定**的汇总行，不认末行；行数要 ÷2 |
| 7 | **「构建通过」≠「产物换了」** —— 输出重定向到 TEMP 的构建**永远不部署** ⇒ 运行期读数必来自上一版 | 只要证据取自运行期，就必须有一步**真的换掉了被加载的东西**，并核对 mtime |
| 8 | **同名 ≠ 同文件并发安全** —— 不同名照样撞 | **共享可变状态的写入窗口才是单位，不是名字** |
| 9 | **半成品比没有更危险** —— 中断的代理留下**半写工作树 + 零上下文** | 宁可「干净且旧」，不要「跑到一半」 |

**16b 🚨 第 16 条的边界被对端纠正了 —— 终点不是「算得对」，是「那个数不存在」**（2026-10-04）

**我原来的措辞**：「**当一个计数会过期时**」⇒ **这个前提就是错的。**
不是所有计数都会过期，**但有些计数根本不该由人写**。

⇒ **更准的适用条件**：
> **只要「数」与「被数的」能分离，就不要存那个数 —— 让它成为口径算出来的视图。**

| | 做法 | 性质 |
|---|---|---|
| 第 16 条 | 划掉已失效的行 ⇒「数未划掉的行」天然排除 | **缓解** —— 那个数**仍存在、仍需维护** |

📌 **关键**：只做到第 16 条时，表头**照样写着 20**，**下一个人照样会去抄** —— 因为它在纸面上看起来仍然可用。
**只有删掉，"抄这个动作"才不存在。**

⇒ **自检问句**：**「这个数是写下来的，还是算出来的？」**
写下来的 ⇒ 它就是一个**未来的过期点**，且**看起来完全可信**。**能从内容推出来的，就不要写下来。**

**我这边已自查出一例**：裁决报告里写过「共 **38** 条零命中结论」这类**派生数字** ⇒ 会过期，且被引用时与"我当场数的"**长得一模一样**。
⇒ 以后这类数**只在当场叙述里说，不作为可被引用的字段落盘**；要引用就写「见 §审计表行数」。

> **四个修法的递进**：
> 第 1 条 **别抄要数** → 第 14 条 **抄前确认源最新** → 第 16 条 **让它算得对** → **第 16b 条「让它不存在」**。

**15c' 🚨 一次「必然失败」的测试不是发现，是【前置没满足】**（2026-10-04 对端实例）

两次都是「某个操作返回了失败」，**一次证明"它坏了"，一次只证明"你根本没在能测的状态下测"。**

**是 ⇒ 它不是被测物的性质，是前置的缺口。** 先补前置，**别把这次失败写进结论。**

| | 形态 | 正解 |
|---|---|---|
| **§15c** | **断言**在正确实现下必然假红 | **换判据**，不放宽 |
| **§15c'** | **实验**在给定前置下必然失败 | **补前置**，不记成结论 |

⚠️ **两者都会伪装成"红"** ⇒ **见红先问：这次红是必然的吗？**

**20 🚨 实验之前先算「信息量」：每个可能结果，是否都对应一个尚未测过的状态？**（2026-10-04 对端实例，我采纳）

对端派它「在这 3 个候选文件里再二分」⇒ **它先出引用清单，算出这个实验是空的**：

⇒ **它在跑之前就否掉了这个实验**，换成已测格子里唯一的空格（P36 只留 Transpiler + Gate）。

📌 **判别式**：**这次实验的每一种可能结果，是否都对应一个我还没测过的状态？**
**若某个结果是「已知状态的复现」** ⇒ **那个实验设计是空的** —— 它不产生信息，只产生一轮时间与一次构建。

⚠️ **"空实验"长得和"有效实验"完全一样**（都要跑一轮、都要出数），**而默认假设总是"它会告诉我点什么"**。

**20b 能用源码论证排除的，不要花一轮实验去测**（同一实例的第二半）

它**把三个文件全读了**，逐个给出静态事实：

> `FlightBeautyBridge` = 一个 `bool` 字段 + 一个布尔谓词；

⇒ **静态论证可以在实验之前就排除一整类假设**，成本是读三个文件，代价是**一轮冷启 + 一次构建 + 一次采样**。
⚠️ **前提**：静态论证只在**读全了相关文件**时成立；**只读签名就下结论，会犯我那第 ⑤ 条**（恒真断言）。

**20c 排期时把"同一天·同机·同会话·交错跑"写进证据**（对端定案时的写法，我采纳）
```

A′ = W11 去整个 P36（9 文件） 冻 0/4

```
⇒ **同一天 · 同一台机 · 同一会话 · 交错跑** ⇒ 才能下「必要且充分」这种结论。
**若几档是跨天/跨机/顺序跑的**，结论强度要按 §18j 降级（独立通道数 < 2 ⇒ 不算独立验证）。

> **20/20b/20c 与第 5、13、15、15d、17、18j 同源**：
> **都在问同一句：「我即将做的这件事，真的会改变我的知识状态吗？」**

> 任何判据要**背书机制**，它必须能区分「**目标原因**」与「**其它同样会触发它的原因**」。
> `Δ=1` **只证明可观测量变了，不证明归因。**

⇒ **这是第 5 条「恒真断言」的姊妹形态，但更危险**：

| | 判据状态 | 危险在哪 |
|---|---|---|
| 第 5 条 **恒真断言** | **永远不会失败** | 它绿着、却零信息量 |
| **第 15 条 归因错配** | **会失败、也确实绿了** | **观测是真的、结论不成立** |

⇒ **第 15 条比第 5 条难发现**：恒真断言至少可疑；**而"观测为真、归因为假"看起来完全正常**。

**自检**：凡写「X 变了 ⇒ 所以是 Y 导致的」，问一句 ——
**除了 Y，还有什么能让 X 变？** 列不出第二个 ⇒ 要么补判据区分，要么**降级为"相关"不写"导致"**。

⇒ **报告格式**：把「**触发读数**」与「**归因读数**」**分两栏写**，不要混成一句。

**15b 归因栏的黄金标准：**排除替代解释**，而不是「我没想到别的」**（2026-10-04 对端实例）

我第 15 条的自检问句是「**除了 Y，还有什么能让 X 变？列不出第二个 ⇒ 降级为"相关"**」——
**那只到"我没想到"，是人力穷举。** 对端给的做法**高一个层级**：

> 触发栏：`IsReserved(c) && who==pawn` + `!CanReserve(c, other)` + 释放后 `!IsReserved(c)`
> 归因栏：`claimant==pawn ∧ target==c ∧ ReferenceEquals(r.job, myJobSnapshot)`
> ⇒ 「**别的东西恰好占了那格**」**不可能满足它** —— **这才是归因**。

⇒ **判别式**：归因条件是「**替代解释在结构上就满足不了**」，还是「**我想不出别的**」？
**前者是判据，后者是祈祷。**
⇒ **任一栏 ❌ 都不报绿** —— 触发过了但归因不成立，照样不算。

**15c 🚨「必然假红」的断言应当被替换，不应当被放宽**（2026-10-04 对端实例）
某个计数断言**在正确实现上就必然假红**（判据会连带删掉 vanilla 自己的东西 ⇒ 计数必然 > 期望）。
⇒ 它**替换**成了另一条断言，**不是放宽**（用 `== 0` 不用 `>=`）。

📌 **理由**：**放宽（`==0` → `>=0`）等于把判据改成恒真** —— 它从此不会再失败，
于是**第 5 条「恒真断言」的诞生路径往往正是"遇到红就放宽"**。

⇒ **遇到断言红时，先问它是不是"必然假红"**（即：正确实现下它会不会也红）。
**是 ⇒ 换判据；否 ⇒ 你的实现或你的理解错了。**
**任何情况下都不要用"放宽"来处理红。**

**15d 🚨「0 命中」其实有【四种】，第四种最隐蔽：模式表本身漏了这个形态**（2026-10-04 对端实例）

我们共用过前三种 —— **没读到**（检索范围错）· **格式不同**（pattern 写错）· **真没有**。
**第四种**：**筛选模式表漏了该形态 ⇒「读到了什么」被悄悄替换成「筛出了什么」。**

实例：门禁①的 grep 模式是 0 命中，**但日志里实打实有崩溃**
（`DegeneratePatherPathTests failed: System.NullReferenceException`）——
根因是模式表里有 `失败[：:]`（**中文冒号**）和 `demo failed`，**却没有 `failed:`（英文冒号）**，也没有 `Exception`。

⚠️ **危险在于它长得和"真干净"完全一样**：grep 返回 0，门禁绿，**而崩溃就在文件里**。
**因为 grep 门禁不是在"读日志"，是在"读你预料到的那些形状"。**

⇒ **规矩**：
1. **grep 型门禁报「0 命中」时，必须同时报「我的模式覆盖了哪些形态」**；覆盖不到的部分**单独计数**（如「未匹配行数」）。
2. **模式表与它守护的东西，版本要一起更新** —— 加了新失败形态却没加模式，门禁就静默漏。
3. **发现"①=0 但日志里有 X"时，第一反应不是"门禁错了"，是"我的模式表漏了 X"** ——
   **并把它写成「模式不覆盖该形态」，而不是改写成「无失败行」。**

⇒ **与第 5 条（恒真断言）同源**：恒真断言**永远不失败**；
**模式表漏形态的 grep 门禁是「只对它认识的形状有效」的恒真** —— 它比前者更隐蔽，因为它**看起来一直在干活**。

> 同族：④b 的「返错比返空毒」、第 13 条的「分母混用」、15c 的「放宽即恒真」——
> **观测为真、结论不成立**，是同一个病的多个入口。

**14 展开（2026-10-04 TEXT20 侧同步，我采纳）**

### 🚨 3.8 两条 2026-10-03 与 TEXT20 侧互纠出来的（**一条我犯过，写进来防复犯**）

**① 分区统计必须先算出分界点，再数。**
不圈范围的 grep/正则，**返回的不是「那一节的内容」，是「全文里长得像那一节的东西」**。

- 反例（对端犯的）：`^\| \*\*\[(\d+)\]\*\*` 扫全文 ⇒ 把**我的台账行**当成索引行
  ⇒ **计数虚高 69 vs 实际 52**，还造出**幻影重复**（幻影重复又反过来让我编出一条假因果，见 ②）。

**② 🚨 不要从观测里推断因果事件 —— 这条是我犯的**

我看到「索引里的重复编号消失了」，就写「**已被修掉**（在我们交换之后）」。
**实际什么都没被修**：板的 `mtime` 停在交换之前 ⇒ **是对方一直量错，不是有东西被修**。

⇒ **观测到「某现象变了」≠「某件事发生了」。**
说"谁在什么时候做了什么"之前，**必须先查 `mtime` / 落盘物**（同 §3.7 第 10 条）。
**否则就是在编故事** —— 而且编出来的因果比没有更可信，因为它会让下一个人**停止追问**。

**③ 口径比结论值钱。**（对端原话，我采纳）
对端那两个错**都是口径错、不是结论错**。
⇒ **报数字必须带口径**：用了哪个 API · 圈了什么范围 · 按什么匹配
（**按键名匹配，不要按词匹配** —— 词匹配会命中**内容文本**而不是数据结构）。

**④ 🚨 任何「查无此项 / 查无出处」的结论，必须附三件套 —— 缺第三件就不是结论**

> ① 用了哪个**检索工具 + 参数**
> ② 圈了什么**范围**（分界点 / 行号区间 / 哪些目录）
> ③ **该类事实的权威来源本应在哪里**

**缺第 ③ 件 ⇒ 那不叫「不存在」，叫「我没在那儿找到」。**

**③b 关系类 / 因果类问题上，第 ③ 件是「**因果链在哪**」**（2026-10-03 与 TEXT20 侧互纠追加）

对端教训：它推断「假阳性**可能污染过 `REV-LEDGER`**」——
**错在「拿记录里的归属当因果链」，而记录本身就在手边、它没去读**。
真实归属在**另一条记录**里（`LEDGER-R2` 的报告逐字写着它的取证路径）。

⇒ **凡断言「X 导致了 Y」或「X 可能影响了 Y」：**
1. 先找出**记录 X 行为的原文**（不是记录 Y 的），**读它**；
2. 报「谁做的」用**归属证据**，报「谁引发的」用**因果链证据** —— **两者不能互相当**；
3. 找不到因果链 ⇒ 说「不可考，链应在哪」，**不要用归属替代因果**。

**④b「查不到」与「返错」是两个形态 —— 别混写**

（2026-10-03 TEXT20 侧提出，我采纳）

| 失败形态 | 调用方的心理 | 自纠正 | 该补什么 |
|---|---|---|---|
| **静默返空 / 0 命中** | 「**这工具查不到**」⇒ 会怀疑工具、去换工具 | 部分（换写法可能命中） | **范围声明**（"我只索引 vanilla"） |
| **静默返错 / 给了个错的** | 「**这工具查到了**」⇒ **相信工具** | ❌ **完全不能** | **同名消歧**（"这是同名类型，不是你要的那个"） |

⚠️ **混写的实际危害**：`[50]` 原措辞「**符号检索族**只索引 vanilla ⇒ mod 本地符号**一律查不到**」——
读到的人会以为 `read_csharp_symbol` 也是"查不到" ⇒ **不会对它设防**，**而它恰恰是更毒的那一个**（返一个 vanilla 同名类型）。

**④c 🚨 交叉引用要验证「被引处真的含该内容」**（2026-10-03 实测发现）

**④d 🚨 「投递成功」≠「投对了人」**（2026-10-04 实测，对方发错对象后双方互认）

对端把一条**发给它自己子代理**的消息，因 `to` 填了**对端会话 id** 而落进我的收件箱。
`send_peer_message` 返回 **`Delivered … steered into a new turn`** —— **成功、无报错**，而内容**不属于收件方**。

⚠️ **这是 §3.7 ④b「静默的错」的实例，且是最危险的一种**：
报错不来的错，收件方**会真的去执行那些不属于它的指令**（那条消息里确实带着"去刷坐标""去做定向复审""commit"这类可执行指令）。

⇒ **收到任何"请执行 X"的指令，先核三件**：
1. **X 是不是我的职责？**（我：不改产品代码、不执行计划、不动 TEXT20 工作区、不 commit）
2. **这些文件/编号是不是我的产物？**（用**文件名/路径**核，不靠内容描述认领）
3. **是谁的编号？**（`W8` / `F-1` / `DegeneratePatherTests` 一律属 TEXT20 侧，不是我）

**核不过就明确回「这不是给我的」并附核实依据，不要"顺手帮忙"。**
**理由：越界的帮助和越界的破坏，在系统看来是一样的。**

⇒ 对应到发送侧：**发消息前核一次 `to`** —— **投递成功只保证"有人收到了"，不保证"收的是对的人"**。

> ①②③④ 与 §3.7 第 1、10 条同根：
> **用一个便宜的成功判据替代昂贵的事实核对。** 省钱的那一刻，正好是证据失效的那一刻。

> **会报错的错 = 自己能纠正；静默的错 = 纠正不了，而且会伪装成事实。**

| 失败形态 | 后果 | 例 |
|---|---|---|
| **静默返空/返 0** | 调用方**会**读成「不存在」⇒ **可能据此改错代码** ⇒ **不可自纠正** | `[43]` `get_overloads` 少报 · `[44]` glob 不递归 · `[45]` 元素类型写错 · `[47]` 扩展方法查不到 |
| **显式报错** | 调用方**不可能**读成「不存在」⇒ 改对参数即过 ⇒ **自纠正** | `[42]` 传 `pattern` 报「query 缺失」 |

⇒ **严重度是「后果」，这条是「形态」；形态比后果更适合用来排修的先后。**
⚠️ 但**不能反过来用**：「会报错」只说明**这一次**自纠正，不代表无需修（`[42]` 仍浪费一轮往返）。

> ①②③④ 与 §3.7 第 1、10 条同根：
> **用一个便宜的成功判据替代昂贵的事实核对。** 省钱的那一刻，正好是证据失效的那一刻。

- 「别跑『停游戏 → 构建 → 实测』的窗口」⇒ **窗口 ≠ 冻结全部工具**；**TRIAGE / 写计划 / 只读核验照常**
- 「别跑会改状态的 MCP 工具」⇒ **只读 MCP 工具（`search_source` / `mcp_help` / `list_contexts` / `read_file`）不受限**
- 「别 `select_context` / `load_asmevery(makeCurrent:true)`」⇒ **但 `load_assembly(makeCurrent:false)` + 显式 alias 是允许且推荐的**
- 「别碰产品代码」⇒ **但可以新建 `docs\issue-triage\`、改自己的计划/报告/AGENT-BRIEF**

⇒ **自检**：**我要拒绝/回避的这个动作，代价到底多大？把它和「听起来像的那个」分开算一次。**
**若两者代价差一个量级 ⇒ 说明我正在合并它们。**

⚠️ **反向也成立**：**别因为怕担责就扩大回避范围** —— 那会把本可做的事一起停掉，对方一轮档期白费。
**回避范围要刚好覆盖真实冲突，不多不少。**

**22 🚨 派单/公告必须同时给【回避清单】和【允许清单】，且后者一样长**（2026-10-04 对端同步整改，我采纳并自曝短板）

对端自曝：它的 `[FYI]` 一晚都写「**对端零占用、随便跑**」——
⚠️ **而「随便跑」本身就是缺陷**：它把「**我不要求你回避**」写成了「**你不需要知道边界**」
⇒ **必然诱发过度回避**（对方无法区分"真冲突"与"我没说"）。

⇒ **新格式（两侧统一）**：
```
🚫 需要避开的（逐条，含原因）
✅ 【明确允许】的（TRIAGE / 写计划 / 只读核验 / 新建自己的 docs 目录 /
                只读 MCP 工具 / load_assembly(makeCurrent:false)+显式 alias / …）
```
**两块一样长。缺一块 = 在制造过度回避。**

🚨 **我方的短板（自曝）**：**我的子代理派单里全是禁令，几乎没有允许清单。**
典型症状：我写了「禁止调用会改变游戏状态的 MCP 工具」，但**没写「只读 MCP 工具可用」**——
子代理只能从禁令里推断许可，**而推断出来的东西通常是"那我还是什么都别做"**。
⇒ **今后派单必带一行 `✅ 允许：<正例清单>`。**

**23 🚨 把一条规则/禁令升级之前，先标它依赖的因果断言【核实过没有】**（2026-10-04 对端实例）

对端把「桥是 `suspend` 弄死的」**升级成了一条禁令**（"禁止 suspend"）——
而人类伙伴的领域事实是：**见过好几次「打断点中了，但忘了自己打了断点」**，
真正卡住桥的**可能是一个残留断点，与 `suspend` 无关**。
⇒ **那条禁令作废。** 发牌员原话：「**我又一次把第二手的因果断言当成了规则**」。

⚠️ **升级是"因果断言"变成"规则"的那一步** —— 而这一步**没有任何工具会提醒你**：
**规则读起来比因果断言更确定、更像既定事实**。

⇒ **自检**：凡我要写「**禁止 / 必须 / 总是**」这类**硬规则**，问一句：
**「这条依赖的成因，是我自己看到的，还是我听来的？」**
**听来的 ⇒ 要么标注「成因未核实，仅按现象规避」，要么先核实。**

**23b 顺带：对端同时记了反向坑**（同一实例）——
> 「**断点状态 = 无**」**不能作为**「桥是好的」证据**（存在"显示没有但依然卡"的罕见情况）
> ⇒ **判桥可用必须【真的 attach 成功并取到一次栈】。**

**这正是 §18j 的应用**：**一次"没有异常"的读数，不是"一切正常"的证据。**

> **22/23 与 §3.8 ②、§21 同源**：**都是「把一个未核实的断言当成已确定的东西」** ——
> §3.8 ② 是**观测→因果**，§21 是**两个动作合并**，**§23 是「第二手断言→硬规则」**。

## 5. 判断「值不值得修」的尺子（TRIAGE 用）

按顺序过，任何一条为 Yes 都不自动构成"值得修"，要看综合分：

1. **真实性**：条目描述的现象能在源码 / 文档 / 现有计划里**核实**吗？
   核实不了（无法验证、描述含糊）→ 判 `无法核实`，不是「不值得修」。
2. **是不是真痛**：
   - 🔴「会让自动化得出**事实相反的结论**」（假成功 / 假阴性）→ 最高优先级。
   - 🟠「每次都要重踩 / 静默烧 token / 系统性浪费往返」→ 中。
   - 🟡「体验略糙」→ 低。
3. **是不是真问题**（不是设计使然）：
   - 查一下是不是**上游 vanilla RimWorld / UnityExplorer 本来就这样** → 那就不是本项目的锅。
   - 查一下是不是**文档没写清**而非代码错 → 那修复成本极低，值得。
4. **可修性**：能在本项目内（模组 / MCP / 文档）修掉吗？需要改 vanilla 吗？需要改第三方吗？
5. **是否已被覆盖**：已有计划里有没有对应任务？有没有已存在的 workaround 让它「不阻塞」？

**最终裁决只有四种**（写在报告最前面，一行）：

```
裁决：值得修 / 不值得修 / 无法核实 / 已被现有计划覆盖
```

- `值得修` → 主代理会再派一个 PLAN 子代理写计划。
- `已被现有计划覆盖` → 不写计划，报告里指向那份已有计划的具体任务号。
- `不值得修` / `无法核实` → 不写计划，报告里给出**为什么**，让维护者能反驳或接受。
