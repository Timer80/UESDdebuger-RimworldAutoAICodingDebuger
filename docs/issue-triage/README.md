# issue-triage —— 吐槽板 issue 自动检查流水线

> 这是**旁路**流水线：它只看、只写计划，**不改任何产品代码**。
> 主线（并行巨型会话树）照常用 MCP 调试，两边互不干扰。

## 它是什么

```
mcp-吐槽板.md 变了
   ↓  watch-tutanban.ps1（后台阻塞作业）
写 state/ + inbox/pending-<时间戳>.md，然后**退出**
   ↓  「后台作业结束」通知 = 把主代理叫醒
主代理读 inbox，按条目派子代理：
   ↓
TRIAGE 子代理  →  triage/<NN>-<slug>.md      「值不值得修」
   ↓  裁决 == 值得修
PLAN   子代理  →  plans/<日期>-<NN>-<slug>.md  「怎么修」（writing-plans 格式）
   ↓
主代理在 mcp-吐槽板.md 对应条目追加一行 `> 🤖 **Triage 批注** …`
```

## 目录

| 路径 | 说明 |
|---|---|
| `watch-tutanban.ps1` | 监控脚本。检出变化 → 写 inbox → 退出 → 唤醒主代理 |
| `inject-skills.ps1` | 把 `~/.dsh/skills` 的 SKILL.md 拷进 `skills/`，供子代理**手动注入** |
| `AGENT-BRIEF.md` | **子代理铁律**：禁改任何既有代码、禁调 MCP、只许写 `triage/` 和 `plans/` |
| `skills/` | 技能快照（每次派单前重新生成） |
| `triage/` | TRIAGE 子代理的裁决报告 |
| `plans/` | PLAN 子代理的实现计划 |
| `inbox/` | 每次检出变化的快照（新增/改动条目全文） |
| `state/` | `board-state.json`（基线）+ `history.log`（检出流水） |

## 写吐槽板时必须守的外部规则

吐槽板 `docs/mcp-吐槽板.md` 是 **UESDdebuger 与 TEXT20 两个项目共用的文件**，
其共通规约在**另一个项目**下（**不在本仓库，搜本仓库必然找不到**）：

```
C:\SteamLibrary\steamapps\common\RimWorld\Mods\TEXT20\.superpowers\sdd\2026-10-01-原版寻路接管-缺口修复-总计划\COMMON.md
```
（481 行 ·《共通规约 · 所有实现/审查/登记子代理必读》）

其 **§10「★ MCP / 模组吐槽板 —— 本项目共享文件」** 直接约束本流水线：

| 规矩 | 本流水线怎么遵守 |
|---|---|
| **「绝对不要改别人的条目。你只加你的。」** | ✅ **新批注一律进板上固定位置的「## 🤖 Triage 台账」节**，不再插进别人的条目正文 |
| 新条目要同时加一行进顶部索引表 | 由**维护者/并行会话**写；本流水线只读，不新增条目 |
| 「别整篇重写」 | ✅ 从不使用 write 覆盖整篇，只做定点 `edit` 追加 |
| 编号接着往下取、不复用 | 本流水线不分配编号 |

> ⚠️ **前 20+ 轮已写进别人条目内部的批注一律保留、不撤回** ——
> **从别人的条目里删除内容，比往里添加内容违反得更厉害。** 它们全是纯追加、明确标 `> 🤖`、原文一字未动。

### 关于「不搜到 ≠ 不存在」

`COMMON.md` §5.1 自己写着「**零命中是最危险的假阴性**」。
⇒ 本流水线已因此翻车 **5 次**（误判 `rimworld-source-online` 源码不存在、误判 `RBS` DLL 不可核实、
误判 `ConsoleController.cs` 不在 `McpRimDebug\`、误判 `GABS` 是运行时实现、
**误判 `COMMON.md` 不存在** —— 最后这次还是因为把检索范围限死在 UESDdebuger 仓库内）。

**规矩：凡是要写「不存在 / 查不到 / 无法核实」的结论，必须同时写出搜索范围。**
范围之外的只能说「本仓库内未找到」。

### 两个本项目实测踩过的「测量/检索」陷阱

| 陷阱 | 实测现象 | 正确做法 |
|---|---|---|
| **`Get-Content \| Measure-Object -Line` 会少算** | 吐槽板同一文件：`[System.IO.File]::ReadAllLines(...).Count` = **1095**，该命令 = **823**。据此我曾把 COMMON.md 数成 481 行（实际 **673**） | **数行数一律用 `[System.IO.File]::ReadAllLines(...).Count`** |
| **`search_string_literals` 的 `pattern` 默认按「字面量」匹配，不是正则** | 曾用 `inputSchema\|schema\|parameters` 检索 → 回 0 命中 → **被当成「这些字符串不存在」的证据**写进报告 | **带 `\|` 的检索结论一律无效**；拆成多次字面量检索，或先确认该工具的正则开关 |

⇒ 这两条都是 COMMON.md §5.1 说的「**零命中最危险的假阴性**」——**在工具层面同样成立**。

### 判断「某条『已绕过』有没有依据」的判据

**看引用与被兜住的是不是同一个检索通道，不看文件存不存在。**（由计划 11 的作者提炼，实测有效）

| 条目 | COMMON.md 里对应什么 | 通道是否相同 | 结论 |
|---|---|---|---|
| **[03]** | `:409`「`list_debug_action_children("Actions")` 返回 400KB+，用 grep 搜 spill 文件」 | ✅ **同工具同绕法** | **状态站得住** |
| **[19]** | §5.2 正控纪律管的是**产物 DLL 的字节级检索**（`#US` UTF-16 / `#Strings` UTF-8 / 奇数偏移），而 [19] 踩的是 **`search_source` 行级匹配** | ❌ **跨通道** | **部分有依据**：认知纪律侧站得住，机制侧（`case_sensitive` 默认 false）`COMMON.md` 没写 |

⇒ 一个**文件存在**不能证明**它兜住了你这件具体的事**。

## 手动操作

```powershell
$r = 'C:\SteamLibrary\steamapps\common\RimWorld\Mods\UESDdebuger\docs\issue-triage'

# 重新取基线（改过基线逻辑、或想忽略某些旧变动时）
pwsh -NoProfile -File "$r\watch-tutanban.ps1" -ResetBaseline

# 挂上等待（会一直阻塞到有变化；加 -MaxMinutes 60 可设上限）
pwsh -NoProfile -File "$r\watch-tutanban.ps1" -PollSeconds 5

# 派子代理前刷新技能快照
pwsh -NoProfile -File "$r\inject-skills.ps1"
```

## 三个设计要点

1. **按条目做基线，不是按整文件做 hash。**
   追加一条新吐槽不会把老条目的改动淹掉，改一条老条目也只会报那一条。
   索引表 `## 索引` 和 `## 值得表扬的部分…` 也各算一条，不会被误判。

2. **哈希前剥掉 `> 🤖` 开头的引用块（含续行）。**
   主代理往吐槽板写的批注不会把主代理自己叫醒（否则无限回环）。
   续行也要剥 —— 批注常写成多行引用块，只认标记行一样会自唤醒。

   > ⚠️ **由此产生一条硬规则：批注必须「纯追加」。**
   > 剥离规则只认得「以 `> 🤖` 开头的新增块」，**防不住删除或改写条目原有的行** ——
   > 改一行原文，剥完批注后的文本照样和基线不同，一样会误唤醒。
   > 所以：**批注只能追加，不能删改条目原有内容。**
   > 即便发现原文写错了（比如一条基于错误诊断的错误绕法），也**保留原文**，
   > 在批注块里写明「上面这句已被证伪，请勿照做」—— 既保留现场，又不触发自唤醒。
   > 这条规则是被两次真实误唤醒换来的：第一次是批注写成多行块，第二次是顺手删掉了条目里那句错绕法。

3. **唤醒靠「作业退出」，不靠轮询。**
   `watch-tutanban.ps1` 阻塞在 `Start-Sleep` 循环里，一旦检出变化就 `exit 0`。
   harness 在后台作业结束时会通知主代理 —— 这就是自动续跑的机制。
   所以主代理每次准备「停工」前，只要确认这个作业还挂着即可。

## 已知边界

- 依赖条目以 `## [NN] …` 行首 `## ` 为界。吐槽板若改成别的小标题样式，解析会退化（脚本会仍能跑，但会把整篇当一条）。
- 一次只处理一批变化；同一批已在检测时写入基线，不会重复触发。
- 脚本只读吐槽板 + 只写 `issue-triage/` 目录，不会碰产品代码。
