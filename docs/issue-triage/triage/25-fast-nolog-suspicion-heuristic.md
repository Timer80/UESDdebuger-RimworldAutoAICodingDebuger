## 3. 判据的假阳性风险与三态建议

### 3.1 假阳性**确实存在，而且是成片的** —— 用实测数据说话

数据来源：`MCP/logs/mcp-20261001-093829.log` 全文 1361 行中全部 **87 条** `execute_debug_action` 调用（用 `[System.IO.File]::ReadAllLines` 逐行提取 `→ (\d+)ms` 与 `"path"`）：

| path | n | min | 中位 | max |
|---|---:|---:|---:|---:|
| `Actions\Hot Query Guard Tests` | 6 | **37** | 51 | **72** |
| `Actions\Flight Gate Registration Tests` | 2 | 74 | 80 | 80 |
| `Actions\Inject Cell Cost Tests` | 1 | 71 | 71 | 71 |
| `Actions\Run FogOpen Tests` | 1 | 58 | 58 | 58 |
| `Actions\Degenerate Pather Path Tests` | 2 | 107 | 119 | 119 |
| `Actions\Wall Cell Cost Tests` | 1 | 133 | 133 | 133 |
| `Actions\Door Semantics Tests` | 5 | 189 | 209 | 227 |
| `Actions\Stage Test Map` | 36 | 3 | 2503 | 60013 |
| `Actions\Run All Tests` | 27 | 131 | 1678 | 60022 |

四条硬证据：

1. **2097ms 不是基线，是单点。** 吐槽板 `:1068` 说的「正常执行同一条要 2097ms」**只对 `Actions\Stage Test Map` 成立**。而 `Hot Query Guard Tests` 的 6 次调用是 37 / 39 / 43 / 51 / 60 / **72** ms —— **板上那条「72ms」阈值会把这 6 次全部误伤**。注意 72ms 这个数字在同一份日志里**既出现在 [25] 的现场档，也出现在 `Hot Query Guard Tests` 的正常档**（`:1201`），单看耗时数字根本分不开。
2. **同一个 path 内部跨 4 个数量级。** `Stage Test Map` n=36，min=3 / max=60013；`Run All Tests` n=27，131 → 60022ms。**任何 per-path 阈值在这两个主力 path 上都不稳。**
3. **「短耗时」远比「异常短」多。** 87 次里 **14 次 < 133ms，分属 7 个不同 action**。阈值若取 <150ms，会同时误伤 Flight Gate / Hot Query / Inject Cell Cost / FogOpen / Degenerate Pather / Wall Cell Cost / Run All Tests **七类**。
4. **最致命：日志里没有 ground truth。** 上表所有调用的 outcome 都写着 `success`，而这个 `success` 正是 [01] 认定**不可信的信封**（`triage/01-…md:28-65`）。`MCP\logs\*.log`（全部 5 个文件）全文 grep 字面量 `logCount` **零命中** ⇒ **无法判定这些 37–133ms 的调用到底执行了没有**。没有 ground truth，任何阈值都只是拿 2097ms 这一个点拟合出来的**过拟合**。

⇒ **板上建议「直接判为未执行」必须否决。** 计划 01 `plan:1157` 已经以「性能侧信道不能当判据」为由否决过一次；本轮只是给它补上了量化证据（并把否决理由从「裁决报告 §修法 3 已定」升级为可复核的数据）。

### 3.2 假阳性的另一条路径：**零日志的合法快动作**

派单点名要核实「有没有合法的『快动作』（比如一个 `Log.Message` 就算完）会被误伤」。**会，而且这条路径比耗时更危险**，因为板上判据是**合取式**：「耗时短 **且** 日志为零」⇒ 未执行。耗时那半已经证明会误伤；关键是零日志那半：

- DebugAction 节点里存在大量**开关型 / 设置型 / 条件不满足即直接返回型**动作（toggle、置位、空实现分支）。这类动作**合法地**只打一条 `Log.Message` 甚至**一条都不打**，且必然在几十毫秒内返回。
- ⚠️ **具体清单本轮无法给出**：DebugAction 的定义在 RimBridgeServer（第三方）内，源码不在本仓库；起游戏实测又被本流水线禁止（AGENT-BRIEF §1.2/§1.3）。⇒ 按 AGENT-BRIEF §5.1，**这不是「不存在」，是「未核实」**。
- 但**判定方向已经足够**：合取式的第二项 `logCount === 0` 计划 01 明确**不作为失败证据**（`plan:115`、实现注释 `plan:471-472`：「`effects.logCount === 0` ← 【不是】失败证据。调试动作本来就不产日志」）。既然单看零日志都判不了，那**加上耗时也不会变可靠** —— 耗时只是把「零日志的合法快动作」这个集合从「可能存在」缩小到「很可能存在」，而不是消灭它。

### 3.3 三态建议（照抄计划 01 对 `truncated` 的同一条纪律）

计划 01 的 `truncated: true | false | 'possible' | null`（`plan:1173`，硬约束第 1 条）已经立好了范式：**用布尔 `true` 就是凭空制造假阳性，用布尔 `false` 就是凭空制造假阴性**。[25] 必须遵守同一条纪律，建议字段：

> **`execution.fastNoLog: true | false | 'possible' | null`**

| 取值 | 含义 | 本轮能否到达 |
|---|---|---|
| `null` | **拿不到耗时**，无法描述（不要编一个值） | ✅ 常态（见 §3.4，RBS 大概率不给耗时） |
| `false` | 已有正面凭据（`status === 'reported-success'`，例如 `logCount > 0`）⇒ 「短但有日志」不构成任何嫌疑 | ✅ 可达 |
| `'possible'` | `logCount === 0` **且**耗时落在「同 path 历史下界附近」 | ⚠️ 只能退化成「零日志 + 调用方自配的绝对阈值」，**MCP 不内置阈值**（见下） |
| `true` | —— | 🚫 **永不可达**，与 `truncated:true` 同处理（`plan:1173`：只有 RBS 将来显式回报才可能到达；保留在取值域里只为不推翻调用方的类型判断） |

**为什么不能内置阈值**：本仓库**没有 per-path 历史基线表**。`MCP/logs/` 里没有结构化耗时记录，MCP 也不落盘基线（`elapsed` 只进日志，见 §3.4）。要判定「低于本 path 历史下界」，就得先有那张表 —— 而它恰恰是被 [09]（Player.log 轮转）之类的既有坑污染过、且需要起游戏才能建的。所以第一版只能把阈值**交给调用方**，MCP 只负责把两个原始量（`logCount`、耗时）**如实透出**。

**绝不用布尔的两个后果**：`true` 会把 §3.1 表里 7 个 action 类整片染成「未执行」；`false` 会让 [01]/[25] 的现场在「拿不到耗时」时**反而显得可信** —— 两个方向都在制造新的假阳性/假阴性，正好抵消计划 01 的全部意义。

### 3.4 顺带一条事实纠正：现在「耗时」对调用方**根本不可见**

- `MCP/index.js:5077` 取 `startMs` → `:5123` 算 `elapsed` → `:5132` 把它写进 `log('INFO', 'tools/call … → ${elapsed}ms ${outcome}')`；此后该作用域内 `:5134-5135` 直接 `return result`，**`elapsed` 再没有被读过一次**。
  ⇒ **「耗时异常短」这个信号对调用方是不可见的**，它只活在 `MCP/logs/*.log` 里。板上那句「72ms」**最可能就是从这行日志读的**（`→ 72ms success`），而不是回包字段。

  ⇒ 板上 [01] 的 `durationMs: 72` **极可能是把 MCP 自己的日志行读成了回包字段**，与 `plan:70` 对 `operation.Success` 的推测**同型**。

⇒ **建议的最小可行动作**（比做启发式更小、更稳）：在计划 01 任务 2 第三处**已经在改**的 `callGABPTool`（`plan:908-935`）里，把 MCP 自己的 wall-clock 透传成 `execution.transportDurationMs`，**只透传、不判定**。这样调用方拿得到那个本来就存在的信号，而阈值比较的责任落在有历史基线的调用方手里 —— **MCP 不发明一个它无法证伪的阈值**。
