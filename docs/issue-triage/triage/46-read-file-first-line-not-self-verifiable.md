## 2. 核实过程（含检索范围）

**口径**：所有「首行真实行号」均由 `search_source` 的 1-based 回显独立确定，**不用 `read_file` 自己的计数**。

### 2.2 复现板上那次调用，并**独立发现机制**

### 2.4 我测到的「Δ = +2」里有**一半是数行误差**，不是工具缺陷

按 A 的返回块手工数（**首行按 `start_line=69` 计**）：`For(TraverseParms parms)` 数得 **74**，真值 **76**，看着像 Δ = +2。
**但这个 +2 是两个独立误差叠加**：

1. **+1 来自空行吞行**（§2.2，真缺陷）；
2. **+1 来自把返回体末尾那个恒定分隔空行当成了内容行** ——
   每块正文与 `[TRUNCATED] …` 之间**恒有一个渲染分隔空行**，它不是文件内容。
   ⇒ `triage/49-…:321` 已经指出「这就是板上『+2』最可能的来源」，**本轮独立复现证实了这一点**。

⇒ **真实的工具侧偏差只有 `{0, +1}`；板上 [46] 索引行记的那个「+1」是计数误差。**

## 3. 索引行那对具体读数是否无出处 —— 核实结果

**核实结果：那对读数在板上是有的，正文说「原文未记录」指的是外部报告原文 —— 但正文这句话写得有歧义，且导致了一个后果。**

| 读数 | 在板上 | 本轮能否复现 |
|---|---|---|
| `read_file(Pathing.cs, start_line=69)` 返回 **25** 行 | ✅ 索引行 L24 | ✅ **能**（#A：`line_count=25`，返回 25 行） |
| 手工数得 `For(TraverseParms)` = **75** | ✅ 索引行 L24 | ❌ **不能**：本轮数得 **74** |
| `search_source` 给 **76** | ✅ 索引行 L24 | ✅ **能**（#E / §2.1） |

**⚠️ 注意一个内部不一致**：索引行说「我按『首行 = 69』手工数，得到 `For(TraverseParms)` 在 **75**」——
**若首行真是 69，块内第 6 行只能数到 74，不是 75**。75 对应的前提是「首行 = 70」（即正确套用 0-indexed + 1）。
⇒ **那一位记录者实际上做了正确的 0→1 换算，却在结论里认定自己「又错了一行」。**
这与 §2.2 的机制完全吻合：**错的不是他的算术，是工具没告诉他起点、而他以为自己没做换算。**

**⇒ 对父问题的直接回答**：

读数就在索引行里。**但本报告不为它补出处**：复现只证明现象为真，不证明 TEXT20 那份报告里这么写（§3.8 ②）。
