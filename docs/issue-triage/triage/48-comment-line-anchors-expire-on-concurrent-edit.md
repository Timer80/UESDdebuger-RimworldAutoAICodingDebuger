## 3. 产品缺陷 or 流程缺陷 —— 判定

**判定：流程缺陷。** 五条判据：

| # | 判据 | 本案 |
|:--:|---|---|
| 1 | **产品缺陷**应当表现为**功能不正确**（算错、返错、挂错、坏掉） | ❌ 零。`PathGridCostTests.cs` 的**全部断言与行为不受注释内容影响**；板上审查报告自己也写「**代码本身零 Critical**」 |
| 2 | 失效的东西是**产品对外承诺的一部分**吗？ | ❌ 注释里的 `file:line` 是**给人看的**，不是 API 契约的一部分 |
| 3 | 根因在**代码里**还是**在做法里**？ | **在做法里**。「拿行号当跨文件审计凭据」必然会在文件被改写时过期 —— 这不是 bug，是**该做法的固有属性** |
| 4 | 有没有一个「产品修复」能让它**永不再犯**？ | ❌ **没有**。只要文件可变、行号可变，锚点就会漂。唯一根治是**不用行号**（符号/内容锚），而那是**约定**不是修复 |
| 5 | 修它需要动**代码**吗？ | ❌ 零代码。① 文件级排他、② 登记表实时写、③ 锚点改符号 —— **三条全是流程/配置** |

**⇒ 结论：流程缺陷，判 🟠 中，不进本流水线的实现计划（真缺陷不在本仓库代码里）。**

**⚠️ 一条例外，必须单独拎出来**：`AGENTS-REGISTRY.md` 的「进行中」表
「最后更新于 13:02、仍写着『⏸ 当前无任何代理在跑』，完全没登记 16:44 那一轮（现表滞后 3.5 小时）」
⇒ **这一项不是流程洁癖，是一个可观测性缺陷**：一张自称权威的登记表在说谎，
而且它让审查者**连「现在还有谁在改」都查不到**，这直接放大了 ①②③ 的全部危害。
**它值得单独修**，但它属于 **TEXT20 侧的代理脚手架**，**不属于本项目（UESDdebuger）的产品**。
