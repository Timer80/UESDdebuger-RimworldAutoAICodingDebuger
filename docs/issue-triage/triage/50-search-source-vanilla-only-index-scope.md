## 2. 口径声明

| 项 | 口径 |
|---|---|
| **API** | `mcp__rimworld-source-online__list_directory` / `search_source` / `read_file`。三者只读、无共享可变状态。 |
| **圈了什么范围** | ① `list_directory{ path:"" }` —— **索引根的完整一级清单**；② `search_source` **不带 `file_pattern`** —— 即**整个索引语料**；③ `read_file` —— 指定单条路径。 |
| **匹配方式** | `search_source` 的 `query` **全部是单个字面量关键词，无 `|`**（遵守 `AGENT-BRIEF.md:106-111`「带 `|` 的检索结论一律无效」）。 |
| **宿主侧对照** | `[System.IO.File]::ReadAllLines` 读 mod 文件；`Test-Path` 确认文件**在磁盘上确实存在**。 |
| **decompilerserver** | 本次**一次未调用**。 |

> 📌 本报告**没有**用任何 0 命中去证明「某符号不存在」；
> 所有 0 命中都只用来证明「**索引语料里没有它**」，且**都附了检索范围**（`AGENT-BRIEF.md` §3.7 第 4 条）。

## 3. 独立复核

### 3.1 决定性证据：`list_directory{ path:"" }` —— 索引根**只有两个条目**

```
list_directory{ path: "", limit: 60 }
→ Defs/
   Source/
```

**口径**：索引根的一级清单，`limit=60`。索引语料 = **`Defs/` + `Source/` 两个子树**。
⇒ **`Mods/` 根本不在索引里**，不是「mod 符号难搜」，而是「mod 目录整片不存在于索引」。

**⇒ 这一条就足以定性 [50]：它讲的是「索引范围」，不是「模式/路径写错」。**

### 3.2 零命中（**附检索范围**）

```
search_source{ query: "IsInAir" }            ← 不带 file_pattern = 整个索引语料
→ No results found. Try adjusting your search query or file pattern.
```

```
read_file{ path: "Mods/TEXT20/source/PathPlan/FlightAStar/FlightState.cs", line_count: 3 }
→ Error: File not found: Mods/TEXT20/source/PathPlan/FlightAStar/FlightState.cs
```

### 3.3 正控：通道是通的（板上给的正控，本会话重跑通过）

```
read_file{ path: "Source/Verse/GenGrid.cs", start_line: 74, line_count: 3 }
→ 	public static bool InBounds(this IntVec3 c, Map map)
  	{
  		IntVec3 size = map.info.Size;
  [TRUNCATED] Showing 3/279 lines.
```
⇒ **通道正常**，`Showing 3/279` 与板上**逐字一致**。

### 3.4 「提示同形」的机制：两条消息**都不带任何范围信息**

| 场景 | 工具返回的**全部**内容 |
|---|---|
| 符号在语料内但没匹配上 | `No results found. Try adjusting your search query or file pattern.` |
| 路径完全在语料外（mod 本地） | `Error: File not found: Mods/TEXT20/source/PathPlan/FlightAStar/FlightState.cs` |

**⇒ 两条消息里都没有「我索引的范围是 `Defs/` + `Source/`」这一句。**
调用方拿到的信息**只能推出「我不知道它在哪」**，**推不出「它不在我的范围里」**。
这正是 `AGENT-BRIEF.md` §3.7 第 4 条（「0 结果必须附在哪儿搜的」）在**工具层**的翻版 ——
**零命中之所以危险，是因为工具连自己的范围都不报。**

### 3.5 宿主侧对照：那个文件**确实在磁盘上**

```powershell
$f = 'C:\SteamLibrary\steamapps\common\RimWorld\Mods\TEXT20\source\PathPlan\FlightAStar\FlightState.cs'
Test-Path $f     # → True
[System.IO.File]::ReadAllLines($f).Count   # → 24
```
⇒ **板上说的「该文件确实存在」属实**，`ReadAllLines` 数出 **24 行**。

## 5. 🚨 族判定：与 [13][16][21][44][45] **不是同一族**

### 5.1 六条的分族判据：**「有没有一种写法是能命中的」**

这是本报告给出的**可机械执行**的分族判据（`AGENT-BRIEF.md` §3.7 第 5 条「这条断言能不能失败？」）：

> **模式/路径写法族**的特征：**符号确实在语料内**，只是**存在某种 query / path 写法能命中**。
> **索引范围族**的特征：**符号根本不在语料内**，**任何写法都不可能命中**。

按这条判据逐条归位：

| 条目 | 符号在 `Defs/`+`Source/` 内？ | 存在能命中的写法？ | 族 |
|---|---|---|---|
| `[13]` 命名空间 ≠ 目录 | ✅ 在 | ✅（`Verse.AI` → `Source/Verse/AI/`） | 写法 |
| `[16]` 能读不能搜 | ✅ 在 | ✅（`read_csharp_symbol` 能读到） | 写法 |
| `[21]` `file_pattern` 猜错目录 | ✅ 在 | ✅（去掉 `file_pattern` 立刻命中 `:450`） | 写法 |
| `[44]` glob 不递归 | ✅ 在 | ✅（去掉 `file_pattern` 命中 `./Source/Verse/AI/PathEndMode.cs`） | 写法 |
| `[45]` 泛型元素类型猜错 | ✅ 在 | ✅（元素类型是 `RegionLink` 不是 `Region`） | 写法 |
| **`[50]` mod 本地符号** | ❌ **不在语料内** | ❌ **不存在任何写法能命中** | **范围** |

### 5.2 裁决：**不是同一族，不要混成一条大计划**

- **共用的是症状**：`No results found` / `File not found` —— 这**恰恰是它们容易被混为一谈的原因**。
- **不共用的是病因**：五条是「**在语料内写错**」，本条是「**语料外**」。
- **实践后果**：`[13][16][21][44][45]` **都能靠一次调用自查**（计划 11 规矩 3 步骤 0 的 `query:"."` 探针 / 去掉 `file_pattern` 重搜）；
  **`[50]` 查不出来的原因就是「查不出来」** —— 没有任何改写 query 能救，**只能换个工具（宿主 `Select-String`）**。
- ⇒ **把它们写进同一条会让执行者做出错误的期望**：以为「照规矩 3 走一遍就能排除」，而在 `[50]` 上**规矩 3 走完仍然是 0**，除非他**先意识到自己问的是 mod**。

### 6.2 🚨 新增量（**这条才是要动手的**）：`read_csharp_symbol` 对模组类型会**静默返回同名 vanilla 类型**

板上只说「`read_csharp_symbol` 也救不了：它按已知 vanilla 类型名取成员，对 mod 本地类型无效」。
**「无效」这个词太乐观了 —— 实测它不是「无效」，是「返回一个看起来很像正文的错东西」**：

```
read_csharp_symbol{ typeName: "FlightState" }
→ // File: RimWorld/Pawn_FlightTracker.cs (Lines 9-15)
    	private enum FlightState
    	{
    		Grounded = 0,
    		Flying = 1,
    		TakingOff = 2,
    		Landing = 3
    	}
```

**口径**：`read_csharp_symbol`，`typeName:"FlightState"`，**不带 `memberName`**；范围 = 该服务的全部符号表。
**发生了什么**：调用方问的是 **mod 的类** `Mods\TEXT20\source\PathPlan\FlightAStar\FlightState.cs`（`Test-Path` = `True`，24 行）；
服务**没有说「没找到」**，而是返回了 **vanilla 里一个同名但完全不同的 `private enum FlightState`**。

⇒ **这不是零命中，是假阳性命中** —— 严重度**高于**板上自评的形态：
零命中会逼人去自查（[13][16][21][44][45] 都属这类），**而一个带 `// File:` 行号头、语法完整、名字分毫不差的返回，会被直接采信**。
它与计划 11 §`0.6` 点名的「**假阳性（🔴，同样致命，方向相反）**」完全同型，且正好落在规矩 4 的靶心
（`…:669-671`：「**不是搜不到，是搜到了『半个』**」）。

**落点：`[11]` 号计划的 `### 规矩 4 —— 同名 / 重载：命中不带「类型身份」`**（`…:669`），
在 4A `search_source` 侧之后补一条 **4C `read_csharp_symbol` 侧：同名 vanilla 类型会被静默返回**，
并给出唯一可靠的退路：**查 mod 类型只用宿主 `Select-String` + `ReadAllLines`，不要用 `read_csharp_symbol`**。

### 6.3 给外部仓库的修复建议（本仓库 0 行可改，供计划正文引用）

按性价比：

1. 🚨 **`read_member(path, memberName)`：返回完整成员体（自动跨行）—— 唯一一次堵住两条通道的退路，优先级最高。**
   （**2026-10-03 提级**，依据 `triage/53-rev-ledger-evidence-path-audit.md` §5.3 第 3 点。）

   | 通道 | 失效形态 | `read_member` 堵得住吗 |
   |---|---|---|
   | `[51]` 型 | `read_file` 按 `line_count=1` 取跨行定义 ⇒ **语义截断**（拿到语法闭合但语义错的单行） | ✅ 按成员名取，**天然跨行** |
   | 本条 `read_csharp_symbol` 型 | 对 mod 符号**静默返回 vanilla 同名类型** ⇒ **假阳性** | ✅ 按 `path` 取，**不再靠类型名解析** |
   | `search_source` 型 | 对 mod 符号**静默 0 命中** | ⚠️ 部分（`path` 仍要在索引范围内 ⇒ 仍需第 2 条的范围声明 / 第 3 条的 `root`） |

   ⇒ **它优于「给检索族加 `root` 参数」**：`root` 只扩索引范围，对 `[51]` 型**完全无效**，
   而且 ⚠️ **对 REV-LEDGER 那次损坏无效**（那次**根本没走 MCP**，见 §6.5）。

2. ⚠️ **按失效形态分别补提示，不能合并成一句范围声明**（2026-10-03 增补，源本条裁决①的拆分）：
   - `search_source` / `read_file` 的 `No results found` / `File not found` ⇒ 补**范围声明**：
     「本服务只索引 `Defs/` 与 `Source/`；模组本地符号请用宿主文件读取。」
     ——**成本最低，收益最大**（板上建议 1 的最小版本）；形状对，返空会让人怀疑工具。
   - `read_csharp_symbol` ⇒ 补**同名类型消歧**（⚠️ **不是**范围声明）：当它回一个 vanilla 同名类型时，
     必须显式提示「**这是 vanilla 的同名类型，不是你要找的那个**」，并给出命中文件的 `// File:` 头。
     ——**这一条更急**：返错的调用方**不会怀疑工具**，返回形状里没有任何可自纠正的信号（§3.8 ④b）。

3. 加 `root` 参数（默认 `<RimWorld>/Mods`，或环境变量指定）。
   ⚠️ **优先级低于 1 与 2**：它只扩索引范围 —— 对 `[51]` 型通道**无效**，对 REV-LEDGER 那次损坏**也无效**。
