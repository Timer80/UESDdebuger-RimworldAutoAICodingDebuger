> 也就是说，它把 `read_file` 的返回值从「上下文」升级成了「事实」，而它没有这个资格。

## 3. 独立复核

### 3.1 现象层：板上引用的返回块，本会话**逐字复现**

```
read_file{ path:"Source/Verse/GenGrid.cs", start_line:74, line_count:3 }
→ 	public static bool InBounds(this IntVec3 c, Map map)
  	{
  		IntVec3 size = map.info.Size;
  [TRUNCATED] Showing 3/279 lines.
  (Tip: Continue reading using `start_line`: 77)
```

**与板上 §① 引用的样例逐字一致。** ⇒ 返回块里**只有** `Showing N/M` 与一个 `Tip`，
**没有任何一行行号**，**也没有任何「本块可能截断了跨行语句」之类的提示**。现象属实。

（附带：此处的 `start_line=74` → 真实首行 **75**，`Tip=77` 亦自洽 —— 这与 `49-*.md` §4 的模型一致，Δ=0。）

### 3.2 🚨 后果层：**vanilla 里当场就能复现**，不需要 mod

把上例的 `line_count` 从 **3 改成 1**，其它一个字都不动：

```
read_file{ path:"Source/Verse/GenGrid.cs", start_line:74, line_count:1 }
→ 	public static bool InBounds(this IntVec3 c, Map map)
  [TRUNCATED] Showing 1/279 lines.
```

这一行是**语法完整、能直接编译**的扩展方法签名。**但它不是全部** —— `search_source` 真值：

```
search_source{ query:"public static bool InBounds", file_pattern:"Source/Verse/GenGrid.cs" }
→ 75:	public static bool InBounds(this IntVec3 c, Map map)
  85:	public static bool InBounds(this IntVec3 c, Map map, int contractedBy)
  95:	public static bool InBounds(this Vector3 v, Map map)
```

**⇒ `line_count=1` 把 3 个重载里的 2 个藏起来了，而返回体对此一个字都没说。**
调用方据此写下「`InBounds` 只有一个重载」——**这句话会编译通过、会进正式文档、会在后续核对里被当成事实**，
**整条链上没有一步会报错。**

📌 这比板上举的 `IsInAir` 例子**更强**：它不需要 mod、不需要跨行表达式，
**只要「成员有多个重载」就成立**，而重载在 vanilla 里遍地都是。

### 3.3 损坏层：mod 文件原文（宿主 `ReadAllLines` 逐字核对）

```powershell
$f = 'C:\SteamLibrary\steamapps\common\RimWorld\Mods\TEXT20\source\PathPlan\FlightAStar\FlightState.cs'
Test-Path $f                                    # → True
[System.IO.File]::ReadAllLines($f).Count        # → 24
for ($i=15; $i -lt 28; $i++) { "{0}: {1}" -f ($i+1), $l[$i] }
```

实测输出（**1-based，行号经 `ReadAllLines` 复核**）：

```
20:         public bool IsInAir => Phase == FlightPhase.Takeoff || Phase == FlightPhase.Cruising
21:             || Phase == FlightPhase.Hovering || Phase == FlightPhase.Landing
22:             || Phase == FlightPhase.Falling;
23:     }
24: }
```

**⇒ 与板上 §③ 引用的三行逐字一致。** 三个后果逐条成立：

| 板上主张 | 复核 |
|---|---|
| `IsInAir` **跨三行** | ✅ `:20`–`:22` |
| 只取 `:20` 首行 ⇒ 「只含 `{Takeoff, Cruising}`、`Landing` 不在其中」 | ✅ **该结论为假** —— 真实集合含 `Hovering` / `Landing` / `Falling`；**真正不在里面的是 `WalkingToTakeoff`**（`:20` 里根本没出现这个成员） |
| 这一句**进了正式审查报告**并被下游当裁定依据 | 板上陈述，本会话**无独立凭据**（不在本仓库可读范围内）⇒ **按「板载未独立核实」登记**，见 §7 |

**⇒ `:20` 这一行单独拿出来，`public bool IsInAir => A || B;` 是一个完全合法的、编译通过的表达式体属性。**
这就是「语法闭合、能编译、语义错」的**机制本身**，板上对机制的描述准确无误。

### 4.1 🚨 本条真正的根因是 `read_file` 的「按行切片」，**不是** `[50]` 的索引范围

⚠️ **2026-10-03 整节改写**（依据 `triage/53-rev-ledger-evidence-path-audit.md`，267 行）。
**本节原先的因果链已作废。** 原文把板上 §④ 末尾那句附注 ——
「该文件是 **mod 本地**的，MCP 根本取不到（见 `[50]`）——**这才是它被误读的真正原因**」——
提升为正式裁决依据，理由是下面那条因果链：

```
[50] 检索族只索引 vanilla
   ⇒ `search_source("IsInAir")` 0 命中、`read_file(...FlightState.cs)` File not found
   ⇒ 调用方**没有权威来源可查**
   ⇒ 退而「用宿主读文件 + 手工数行」
   ⇒ 数到一条跨三行的表达式，只看到首行        ← [51] 在此处才起作用
```

**这条链的第 4 环（调用方退而手工数行）不成立。** `[53]` §3 的三项证据表明
REV-LEDGER **压根没用 MCP 读那个文件**：`W8-LEDGER-review.md:385` 自述用的是宿主
`Select-String` / `[IO.File]::ReadAllLines`（§3.1）；它引用的是 mod 本地路径的精确单行锚点 `:20`
（§3.2）；同一份报告全文 396 行里 `read_file` / `read_csharp_symbol` / `search_source` / `rimworld-source-online` / `decompilerserver` / `contextAlias` **各 0 命中**
（§3.3，且同一次扫描在同目录上对 `IsInAir` 有 346 次命中 ⇒ **扫描本身有效，0 命中是真的 0**）。

**⇒ 改后的因果链（这一条才是本条的病因）：**

```
`read_file(path, start_line, line_count=1)` 只做**按行切片**，不判断语句完整性
   ⇒ 返回块里那条跨三行的表达式**只露出首行**
   ⇒ 首行**语法闭合、能编译**（审查者还顺手补了个分号把它凑成合法 C#）⇒ **不触发任何检查**
   ⇒ 语义错的定义进了正式审查报告
```

⚠️ **本条不需要 mod 就能发生** —— §3.2 已在 vanilla 里当场复现
（`GenGrid.cs:75` / `:85` / `:95` 三个重载只取到 1 个）。
